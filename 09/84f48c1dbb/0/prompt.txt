This error is raised by the SDK's per-group trajectory state machine, not by our code. It isn't a torque or controller fault, and it happens before the robot moves.

Where it fires

The error text comes from _fail_on_frame in trajectory_state_machine.py.
It is raised from the cursor's _motion_group_state_monitor (trajectory_cursor.py:1421).
The rule it enforces: the machine is at rest in paused (reason USER), and a TrajectoryRunning frame arrives that this cursor never started. Only this cursor may resume a user pause, so it treats that as a contradiction and tears the session down.
How the machine gets into paused before anything moved
The failing frame says location 0.0, standstill=True, so the machine was already in paused before the trajectory started. From armed, only one path leads there (_handle_armed):

A parked PAUSED_BY_USER frame with standstill=False arrives. The SDK reads this as "the robot is leaving standstill; RUNNING follows one cycle later" and sets _moved = True.
The next PAUSED_BY_USER frame has standstill=True. Because _moved is set, the SDK concludes a real user pause has settled and moves to paused(USER).
The IO barrier releases the trajectory, and the controller reports TrajectoryRunning at location 0.0, standstill=True. From paused(USER) that is an error.
When that happens in our flow (inferred from the SDK code; I haven't confirmed it on the robot)
The trigger is a single standstill=False frame while the robot is actually at rest, i.e. the standstill flag flickering. The most likely moment is right at the start of each linear leg:

Each leg starts immediately after a previous motion: the slow lead-in to the stroke start before leg 1, or leg 1's own session before leg 2. The only gap is the two plan calls.
The new session then attaches, and the cursor holds back state frames until its start command has gone out (_held_at_first_dispatch). That means frames from just after the previous motion can be processed while the machine is already armed, inside the window where a standstill flicker counts as "starting to move".
A physical robot still settling after a move plausibly flickers its standstill flag. The virtual clone never does, which fits this only showing up on the real cell.
This isn't specific to the linear motion. folge11_rrt uses the same synchronized executor (execute_planned_multi), so it can hit the same thing.

To confirm it:

Set LOG_LEVEL to debug in k8s/app.yaml. The cursor then logs every frame as frame standstill=… execute=… location=… | <state> → <state>.
Before the error, look for armed → paused on a TrajectoryPausedByUser frame, preceded by one with standstill=False.
The same log shows which group failed (arm or rail) and on which leg. The traceback alone doesn't say.
Possible fixes:

In our code, quick: wait until the robot has been at standstill for a while (a short fixed settle time, or N consecutive standstill frames) before each synchronized leg. This closes the window without touching the SDK. I'd add it as a LINEAR_SETTLE_S knob.
Upstream in the SDK: _handle_armed shouldn't treat one PAUSED_BY_USER, standstill=False frame as the robot leaving standstill when the controller hasn't taken up the start yet, and standstill jitter at rest can trigger it. That's worth reporting with the debug log from step 1.
Should I add the settle wait? It's a few lines, and the debug log would then show whether it's enough.
