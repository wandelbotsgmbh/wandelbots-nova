<result>## Design principle

**Transient states (`ending`, `pausing`) follow the discriminator; rest states (`paused`, `ended`) enforce it.** In a transient state the robot is still moving, so a `Running` frame is not physically contradictory — the controller re-armed or never actually settled — and waiting for standstill is wrong either way (stuck, or a wrong completion at the next standstill). In a rest state the op is resolved and standstill confirmed; `Running` there means the robot moves without this cursor having issued `start`. The cursor's guard (`trajectory_cursor.py:1327-1333`) already guarantees `start` precedes `process_motion_state` whenever an op exists, so "machine still at rest when Running arrives" ⇔ "no start issued" — no flag needs passing into the machine. Document that contract in the class docstring.

## 1. Decision table (`process_motion_state`)

| state \ frame | None∧ss | None∧¬ss | Running / WaitForIO | Ended∣PausedOnIO ∧ss | Ended∣PausedOnIO ∧¬ss | PausedByUser ∧ss | PausedByUser ∧¬ss |
|---|---|---|---|---|---|---|---|
| executing | keep | keep | keep | →ended | →ending | →paused | →pausing |
| ending | →ended | keep | **→executing (NEW, warn)** | →ended | keep | →ended (unchanged) | keep |
| pausing | →paused | keep | **→executing (NEW)** | **→ended (NEW, optional)** | **→ending (NEW, optional)** | →paused | keep |
| paused | keep | keep (tolerate, debug) | **Running: fail (NEW)** / WaitForIO: keep+debug | **fail (NEW)** | **fail (NEW)** | keep | keep (pre-start jitter, F029 shape) |
| ended | keep | keep | **Running: fail (NEW)** / WaitForIO: keep+debug | keep | keep | keep (stop / other client initialising) | keep |

Today `paused`/`ended` have no branch at all (everything silently kept). The optional `pausing ∧ Ended → ended` covers a pause requested just before the end; today it lands in `paused` at the end location, which is a lie the PAUSE op then reports. Cheap, consistent, but separable.

`ending ∧ Running`: resume, not fail. `ending` is entered from PausedOnIO too; whether RAE auto-resumes when the IO clears is unknown to the SDK, and `backward()` during end-deceleration also produces Running while `ending` (the guard does not fire in ending). Failing there would be harsh; resuming is correct in both readings.

## 3. Risk review

- `pause()` mid-motion: PausedByUser (ss or ¬ss) unchanged; `pausing → paused` intact. Level-based deceleration publishes PausedByUser persistently, never Running, so no spurious resume.
- Resume via `forward()`: guard sends `start` before the frame; rest-state rules never see it. Frames between op completion and `forward()` are PausedByUser/Ended → keep.
- `backward()` after `ended`: op → `start` → executing → pre-start PausedByUser ping-pong (unchanged) → Running → Ended.
- `pause_on_io`: `executing ∧ PausedOnIO → ended` unchanged; one-shot detaches. **Assumption to verify live:** RAE does not auto-resume PausedOnIO when the IO clears while an interactive cursor stays attached with no op — that would now raise `ended ∧ Running`. Check with `test_cursor_forward_pause_on_io_stops_early_mid_trajectory` (it clears the IO before `detach()`).
- `start_on_io`/WaitForIO: keep in executing; tolerated at rest; executor session test (re-arm after ended, `test_trajectory_executor_session.py:355-385`) has an op, so guard fires.
- Bare standstill: `None` frames unchanged everywhere; fixtures still pass.
- `TrajectoryExecutor`: cursors are `detach_on_standstill=False` (:170) so C never applies; a fail in one group propagates through the executor's TaskGroup (:198-205), siblings detached in `finally`. `paused_state(ss=True)` without prior Running (`:247-251`) hits `executing → paused` — unchanged.
